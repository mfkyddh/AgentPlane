# 哲学与工程原则

> 结论：AgentPlane 的原则分三层——道（根本信念）、法（思维方法）、术（工程纪律）。道指导法，法指导术，遇到冲突时优先遵循更高层。

---

## 道法术三层关系

道法术是中国传统哲学的三层思维框架：

| 层 | 含义 | 在 AgentPlane 中 | 回答什么问题 |
|----|------|------------------|-------------|
| **道** | 根本信念，指导一切的前提 | 运维必须安全、可追溯、对 AI 友好 | **为什么做这件事？** |
| **法** | 思维方法，把信念转化为判断 | 先调查后判断、抓住主要矛盾、保持简单 | **怎么想这个问题？** |
| **术** | 工程纪律，把判断转化为代码 | 证据优先、不重复、不过度设计 | **怎么写这段代码？** |

```
┌─────────────────────────────────────────┐
│           术（工程纪律）                  │
│   证据优先 / YAGNI / DRY / KISS          │
├─────────────────────────────────────────┤
│           法（思维方法）                    │
│   调查研究 / 集中兵力 / 奥卡姆剃刀          │
├─────────────────────────────────────────┤
│           道（根本信念）                  │
│   运维必须安全、可追溯、对 AI 友好          │
└─────────────────────────────────────────┘
```

**冲突时的优先级**：道 > 法 > 术。例如，"奥卡姆剃刀"（法）说如无必要勿增实体，但如果事实证明必须加功能来保障安全（道），就应该加。

---

## 道（根本信念）

> 道是 AgentPlane 存在的理由——不是技术选择，而是对"运维应该是什么样"的判断。

**核心信念**：运维操作必须同时满足三个条件——安全（执行前有计划、执行后有验证）、可追溯（所有操作有记录、出问题可以查）、对 AI 友好（AI 可以直接使用，不需要人写脚本）。

这三个条件不是三个独立目标，而是同一件事的三个面：安全靠闭环保障，闭环靠记录实现，记录靠统一入口（CLI）落地。

**派生的两条认识论原则**：

| 原则 | 核心要义 | 在 AgentPlane 中的应用 |
|------|----------|------------------------|
| **实事求是** | 从客观存在的实际事物出发，不凭想象设计功能 | 先看用户真正需要什么，再决定做什么 |
| **矛盾分析法** | 识别并抓住主要矛盾，集中力量解决 | 遇到多个问题时，先解决最关键的 |

**示例**：当同时面对"文档不完整"和"CLI 有 bug"两个问题时，矛盾分析法告诉我们先修 bug——因为 bug 阻塞用户使用，文档只是降低体验。

## 法（思维方法）

> 法是做决策时的思考框架——面对不确定信息时，怎么判断、怎么选择。

| 原则 | 核心要义 | 在 AgentPlane 中的应用 |
|------|----------|------------------------|
| **调查研究** | 先调查再发言，不猜测；通过实践验证 | 做判断前先读代码、查文档、跑测试 |
| **多源验证** | 收集多方意见，系统化后返回验证 | 设计方案时参考业界实践、用户反馈、技术文档 |
| **集中兵力** | 聚焦核心，不分散精力 | 一个阶段只解决一个主要问题 |
| **奥卡姆剃刀** | 如无必要，勿增实体 | 能不加的功能就不加，保持简单 |

**示例**：设计 CLI 时，"调查研究"要求先看用户怎么用现有工具（读代码、看 issue），而不是凭想象设计命令格式。

---

## 术（工程纪律）

> 术是写代码时的硬性纪律——不是"建议"，而是"必须"。

| 原则 | 核心要义 | 说明 |
|------|----------|------|
| **证据优先** | 所有操作必须有记录 | 执行后必须验证并记录，出问题可以查。这是"安全"和"可追溯"在代码中的落地 |
| **YAGNI** | 不要过度设计 | 只实现当前需要的功能，不为未来可能的需求写代码 |
| **DRY** | 消除重复代码 | 相同逻辑只写一次，通过函数、模块复用 |
| **KISS** | 保持简单 | 能用简单方案解决的，不用复杂方案 |

**示例**："证据优先"在部署中的体现：Plan（预览变更）→ Apply（执行部署）→ Verify（验证健康）→ Record（写入 Ledger）。不等问题积累，部署完立即验证。

## 原则如何指导架构

原则不是抽象口号——它们直接决定了架构设计。以下是原则到架构的关键映射：

| 原则 | 架构体现 | 详细说明 |
|------|---------|---------|
| 安全+可追溯（道） | 执行闭环：Plan → Apply → Verify → Record | [架构 > 三层投影模型](architecture.md#标准执行闭环) |
| 对 AI 友好（道） | Skill 路由到 CLI，AI 说人话就行 | [架构 > 快速理解](architecture.md#核心概念) |
| 证据优先（术） | 三层投影：Host Inventory → Object Ledgers → App Summary | [架构 > 三层投影模型](architecture.md#三层投影模型) |
| 调查研究（法） | 真源优先级：Live State > Inventory > Ledger > Runbook | [架构 > 快速理解](architecture.md#核心概念) |
| 奥卡姆剃刀（法） | 5 个域，每个域对应项目模型一层，没有多余 | [架构 > 域](architecture.md#域) |

> 设计约束（CLI-first、Agent-first、离线优先）见 [愿景 > 约束](vision.md#约束)。
