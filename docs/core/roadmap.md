# 路线图

> 结论：从 Alpha 到"小团队标准工具"分三个阶段推进。每个阶段解决 [愿景](vision.md#解决什么问题) 中的一个层次的问题，通过实践验证而非计划驱动。

---

## 三阶段路线

```
Alpha（当前）          Beta                   GA
─────────────────────────────────────────────────────→
  内部验证             外部验证               规模扩展
```

| 阶段 | 解决什么问题 | 核心标志 |
|------|-------------|---------|
| Alpha | 核心机制是否可靠 | 一个真实应用完成全生命周期 |
| Beta | 代码库是否可维护 | 架构债务清零，测试盲区补全 |
| GA | 能否规模扩展 | 插件生态，社区自运转 |

**为什么是三个阶段？**

- **Alpha → Beta**：内部验证完成后，才能让外部用户使用。核心不稳就开放，会浪费用户信任。
- **Beta → GA**：外部用户验证完成后，才能规模扩展。没有真实用户反馈就推广，会放大问题。
- 每个阶段的退出标准都是可验证的，不靠"感觉差不多了"。

---

## Alpha：内部验证

> Alpha 的目标：证明核心机制可靠——CLI 能用、证据链能跑、一个真实应用能走完全流程。

### 退出标准

- [x] 一个真实应用（App）完成全生命周期验证（构建 → 部署 → 验证 → 回滚）
- [x] 所有核心域（infra、service、app）有完整测试
- [x] 文档体系覆盖目标用户场景

### 当前进展

- 已稳定：CLI 入口纪律、离线测试门禁、文档治理、Secret 边界
- 仍在收敛：发布产物自动化、Provider 合同测试、App delivery schema 扩展

---

## Beta：质量加固

> Beta 的目标：让代码库可维护——消除架构债务，补全测试盲区，提升代码质量。

### 关键里程碑

| 里程碑 | 解决什么问题 | 验收标准 |
|--------|-------------|---------|
| M1: 公开贡献者循环 | 外部用户无法参与 | 贡献者文档完整，CI 可公开访问 |
| M2: 发布工程 | 版本不可复现 | 自动化发布流程，版本号规范 |
| M3: 合同硬化 | 交付不可靠 | contract.yaml schema 稳定，验证工具可用 |
| M4: 运行时拆分 | provider 细节泄漏到上层 | 核心逻辑与 provider 解耦 |
| M5: 架构债务清理 | 大文件不可维护 | 所有源文件 < 500 行，无函数超过 8 参数 |
| M6: 测试盲区补全 | 关键模块无测试 | 所有 CLI 命令和 domain 模块有单元测试 |
| M7: 代码质量清零 | lint 错误和坏味道 | ruff 0 errors，无 bare except，无废弃代码 |

### 里程碑逻辑

M1-M4 是**基础架构**：已完成。M5-M7 是**质量加固**：消除技术债务，让代码库可持续演进。

### 退出标准

- [ ] 所有源文件 < 500 行
- [ ] ruff 0 errors
- [ ] CLI 命令测试覆盖率 > 90%

---

## GA：规模扩展

> GA 的目标：成为小团队标准工具——解决"资源有限"问题，让社区自运转。

### 关键能力

- **插件生态**：支持第三方扩展，用户不需要自己写脚本
- **社区自运转**：外部贡献者维护，不依赖单人
- **成功案例**：至少 3 个不同场景的案例文档化

### 退出标准

- [ ] 100+ 活跃用户
- [ ] 社区自运转（外部贡献者维护）
- [ ] 至少 3 个成功案例文档化
