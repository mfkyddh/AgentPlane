# AgentPlane 愿景

> 结论：AgentPlane 解决小团队"运维靠人、出了问题查不到"的问题。用 AI Agent 统一入口，用项目模型管理结构，用证据链保证可追溯。

---

## 目标用户

**小团队和个人开发者**——资源有限，但需要安全、可追溯的运维。

典型场景：
- 个人开发者维护自己的几个服务
- 小团队（2-10 人）管理内部工具或客户项目
- 开源维护者需要部署和运维自己的项目
- 自托管服务维护者需要管理自己的基础设施

---

## 解决什么问题

这些用户通常面临三个问题：

| 问题 | 现状 | 后果 |
|------|------|------|
| **资源有限** | 没有专职运维，开发者自己管 | 出了问题只能靠经验，没有流程保障 |
| **工具分散** | SSH、Docker、Nginx、数据库……每个工具一套命令 | 操作不一致，换个人就不会 |
| **缺乏记录** | 出了问题不知道谁改了什么、什么时候改的 | 无法追溯，无法回滚，只能靠猜 |

**AgentPlane 的回答**：用 AI Agent 统一入口（解决工具分散），用执行闭环保证每步有记录（解决缺乏记录），用 CLI-first 让 AI 和人类用同一套命令（解决资源有限）。

---

## 项目模型

AgentPlane 帮助用户管理的项目结构如下：

```text
项目（Project）
├── 应用 1（App）—— 可独立部署、验证、回滚
├── 应用 2（App）
└── 应用 N（App）

目标环境（Target）
├── prod0-main
├── wsl
└── ...
```

| 概念 | 定义 | 示例 |
|------|------|------|
| **项目（Project）** | 用户希望 AgentPlane 帮助管理的完整单元 | "商城系统" |
| **应用（App）** | 项目中可独立部署、验证、回滚的业务单元 | "订单服务"、"支付网关" |
| **目标环境（Target）** | 被管理的运行环境，当前主要是服务器（Host） | `prod0-main`、`wsl` |

项目与应用是 1:1 或 1:N 的关系。每个应用对应一个**应用项目**仓库，通过**应用交付合同**（`deploy/agentplane/contract.yaml`）与 AgentPlane 交接。

> 项目模型中的每一层都有对应的管理能力（域），见 [架构 > 域](architecture.md#域)。
> 术语定义见 [术语表](../glossary.md)。

## 核心价值

| 价值 | 含义 | 项目模型如何支撑 |
|------|------|------------------|
| **安全** | 执行前有计划，执行后有验证 | 项目模型划分了清晰的边界——App 是部署单元，Target 是执行环境，Plan 只作用于明确的对象 |
| **可追溯** | 所有操作有记录，出问题可以查 | 每一层（Project、App、Target）都有对应的 Ledger 证据链，从项目级到服务级都能追溯 |
| **Agent 友好** | AI 可以直接使用，不需要人写脚本 | 项目模型提供了稳定的业务引用（project name、app name、target name），AI 不需要理解底层实现 |

## 约束

### 资源约束（不可改变）

| 约束 | 说明 |
|------|------|
| 单人、业余时间维护 | 资源有限，必须聚焦核心 |

### 设计约束（指导架构决策）

| 约束 | 说明 |
|------|------|
| CLI-first | 所有操作通过统一入口，Agent 和人类用同一套命令 |
| Agent-first | AI 可以直接使用，不需要人写脚本 |
| 离线优先 | 不依赖外部服务，保护隐私 |

### 产品约束（指导产品决策）

| 约束 | 说明 |
|------|------|
| 可 fork | 用户可以定制，保持简单 |
| 不做 SaaS | 不托管用户数据 |
| 不做通用框架 | 只解决运维控制面问题 |

> 技术栈细节（Python 3.12+、uv）见 [编码与协作规范](../conventions.md#技术栈基线)。
