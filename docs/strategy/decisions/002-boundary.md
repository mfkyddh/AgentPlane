# 决策记录：项目边界

## 状态

**接受**

## 日期

2026-04-30

## 背景

AgentPlane 定位为"给 Agent 的产品全生命周期控制面"，需要明确与现有工具的边界，避免范围蔓延。

## 决策

### 1. 替代关系

**不替代现有工具**：
- Terraform（不管云资源全生命周期）
- Kubernetes（不做容器编排）
- Ansible（不做配置编排）
- CI/CD 工具（不做持续集成/持续部署）
- 监控工具（不做实时监控）

**AgentPlane 的位置**：在这些工具之上，提供 Agent 友好的统一入口和执行闭环。

### 2. 服务场景

**适合**：
- 少量服务器和应用的 AI-assisted 运维
- 需要公开仓库与生产 secrets 分离
- 需要稳定任务入口和审计证据
- 应用仓库只交付代码和合同

**不适合**：
- 大型企业（不支持大型多租户平台）
- 强一致场景（不支持强一致持续调谐）
- 实时系统（不支持实时系统）

### 3. 产品形态

**不成为**：
- SaaS（不做托管服务）
- 通用 Agent 框架（不做通用 Agent 框架）
- 大型 DevOps 平台（不做大型 DevOps 平台）

**成为**：可 fork 的 CLI-first 控制面模板。

### 4. 管辖范围

**不管**：
- 业务开发（代码编写、代码审查、单元测试）
- 代码编辑（不做代码编辑器）
- 版本控制（不做版本控制系统）

**管**：
- 应用的部署、运维、验证、证据
- 服务器的纳管、审计、远程操作
- 入口的管理、发布、验证

## 理由

### 为什么画这些边界？

1. **聚焦核心价值**：AgentPlane 的价值在于 Agent 友好的统一入口和执行闭环，不在于替代成熟工具
2. **资源约束**：小团队和个人开发者维护，无法覆盖所有场景
3. **清晰定位**：明确不做什么，避免用户误解和功能蔓延
4. **可 fork 设计**：保持简单，让用户可以 fork 后定制

### 为什么不是更宽的边界？

**为什么不替代 Terraform？**
- Terraform 专注于云资源全生命周期管理
- AgentPlane 专注于应用和服务的运维
- 两者互补，而非竞争

**为什么不替代 Kubernetes？**
- Kubernetes 专注于容器编排
- AgentPlane 专注于 Agent 友好的运维控制面
- 目标用户不同（小团队 vs 大型企业）

**为什么不成为 SaaS？**
- 需要专注核心功能
- 需要更多资源和基础设施
- 不符合"可 fork"的设计理念

## 替代方案

### 方案 A：替代现有工具

**描述**：AgentPlane 替代 Terraform、Kubernetes 等工具

**优点**：
- 一站式解决方案
- 用户体验统一

**缺点**：
- 范围太大，无法聚焦
- 需要更多资源和时间
- 不符合当前阶段

### 方案 B：成为通用框架

**描述**：AgentPlane 成为通用的 Agent 框架

**优点**：
- 范围广，用户多
- 可扩展性强

**缺点**：
- 范围太大，无法聚焦
- 需要更多资源和时间
- 不符合当前阶段

## 影响

### 对产品设计的影响

1. **明确功能范围**：只做 AgentPlane 特有的事
2. **简化用户界面**：面向小团队和个人开发者
3. **清晰边界**：明确不做什么，避免功能蔓延

### 对技术架构的影响

1. **可扩展性**：支持项目 → 业务系统 → 应用三层结构
2. **配置管理**：支持应用通过配置文件声明配置
3. **操作粒度**：支持业务开发由人类做，运维由 AgentPlane 管

### 对文档体系的影响

1. **用户文档**：面向目标用户，简单易懂
2. **技术文档**：面向开发者，清晰准确
3. **边界文档**：明确不做什么，避免误解
