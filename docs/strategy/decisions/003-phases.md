# 决策记录：阶段划分

结论：采用三阶段路线（Alpha → Beta → GA），通过实践验证而非计划驱动。

---

## 📋 状态

**接受**

## 📅 日期

2026-04-30

## 📖 背景

AgentPlane 的长期目标是"3 年内成为小团队的标准工具，拥有 100+ 用户"。需要明确从当前 Alpha 到目标的路径。

## 🎯 决策

### 1. 三阶段路线

```
Alpha（当前）          Beta                   GA
─────────────────────────────────────────────────────→
  夯实核心             开放验证               规模扩展
```

### 2. Alpha 阶段

**目标**：夯实核心，确保基础可靠

**重点**：
- CLI 骨架稳定
- 文档体系完整
- 离线测试覆盖
- 投影模型验证

**退出标准**：
- 所有核心 Skill 有完整测试
- 文档体系覆盖所有目标用户场景
- 至少一个真实应用完成全生命周期验证

### 3. Beta 阶段

**目标**：开放验证，让外部用户可用

**重点**：
- 公开贡献者循环
- 发布工程
- 合同硬化
- 运行时拆分
- Provider 合同

**退出标准**：
- 至少 10 个外部用户成功使用
- Provider 合同稳定
- App delivery schema 正式发布

### 4. GA 阶段

**目标**：规模扩展，成为小团队标准工具

**重点**：
- 插件生态
- 社区建设
- 标准定位

**退出标准**：
- 100+ 活跃用户
- 社区自运转（外部贡献者维护）
- 至少 3 个成功案例文档化

## 💡 理由

### 为什么选择三阶段？

1. **实践驱动**：不预设完美计划，通过实践验证方向
2. **聚焦核心**：每个阶段有明确重点，避免范围蔓延
3. **用户优先**：用户反馈驱动优先级，而非技术指标

### 为什么不是更多阶段？

**为什么不是四阶段或五阶段？**
- 三阶段足够清晰，用户容易理解
- 更多阶段会增加复杂度，不利于执行
- 每个阶段可以内部迭代，无需外部阶段

### 为什么不是更少阶段？

**为什么不是两阶段？**
- Alpha→Beta 跳跃太大，风险高
- GA 阶段需要独立的退出标准
- 三阶段更平衡，易于管理

## 🔄 替代方案

### 方案 A：两阶段（Alpha→GA）

**描述**：跳过 Beta，直接从 Alpha 到 GA

**优点**：
- 简单，易于管理
- 减少阶段切换成本

**缺点**：
- 跳跃太大，风险高
- 缺少开放验证阶段
- 可能错过用户反馈

### 方案 B：四阶段（Alpha→Beta→RC→GA）

**描述**：增加 Release Candidate 阶段

**优点**：
- 更细粒度，风险更低
- 更多验证机会

**缺点**：
- 复杂度增加
- 阶段切换成本高
- 可能过度工程化

## 📊 影响

### 对产品设计的影响

1. **聚焦核心功能**：每个阶段有明确重点
2. **简化用户界面**：面向小团队和个人开发者
3. **清晰边界**：明确不做什么，避免功能蔓延

### 对技术架构的影响

1. **可扩展性**：支持项目 → 业务系统 → 应用三层结构
2. **配置管理**：支持应用通过配置文件声明配置
3. **操作粒度**：支持业务开发由人类做，运维由 AgentPlane 管

### 对文档体系的影响

1. **战略文档**：建立愿景、原则、路线图、决策记录
2. **用户文档**：面向目标用户，简单易懂
3. **技术文档**：面向开发者，清晰准确
