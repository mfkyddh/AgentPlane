# 🌟 AgentPlane 愿景

结论：AgentPlane 的愿景是成为"给 Agent 的产品全生命周期控制面"，帮助个人开发者、小团队、开源维护者和自托管服务维护者安全地管理产品从创建到运维的全过程。

---

## 🎯 一句话愿景

**给 Agent 的产品全生命周期控制面**

**含义**：
- **Agent**：AI 代理，直接用英文
- **产品**：包含多个业务系统 + 全局配置
- **全生命周期**：从创建到运维的所有阶段
- **控制面**：决策层，不是执行层

---

## 💡 解决什么问题

| 问题 | AgentPlane 的回答 |
| --- | --- |
| AI 直接 SSH 或 Docker 操作不可追溯 | 所有正式动作收口到 `agentplane ...`，输出结构化证据。 |
| 生产 secrets 和公开仓库容易混淆 | 真实 secrets 只在 ignored `secrets/`，公开仓库只保留模板和示例。 |
| Windows、WSL、Linux 路径和执行方式漂移 | 上层使用逻辑路径，runtime/backend 负责解析。 |
| 运维动作只执行不验证 | 正式动作遵循 plan -> apply -> verify -> ledger -> inventory refresh -> doc-sync。 |
| 应用仓库成为第二控制面 | 应用仓库只交付代码、构建资产和合同，生产控制面归 AgentPlane。 |

---

## 🎯 长期目标

**3 年内成为小团队的标准工具，拥有 100+ 用户**

**衡量标准**：
- 用户数：100+
- 时间：3 年
- 范围：小团队

---

## 📌 核心价值主张

**Agent 安全管理产品全生命周期**

**含义**：
- **Agent**：AI 代理，直接用英文
- **安全**：安全可控，不是无限制
- **管理**：决策层，不是执行层
- **产品全生命周期**：从创建到运维

---

## 👤 目标用户

| 用户类型 | 特点 | 需求 |
|----------|------|------|
| **个人开发者** | 独立工作，资源有限 | 简单、自动化 |
| **小团队（2-10 人）** | 协作工作，资源有限 | 标准化、可追溯 |
| **开源维护者** | 维护开源项目，资源有限 | 统一、可审计 |
| **自托管服务维护者** | 维护自己的服务，资源有限 | 安全、可控 |

**共同特点**：
- 资源有限
- 需要自动化
- 需要安全可控
- 需要可追溯

---

## ✅ 成功标准

**用户满意度**

**含义**：
- 不依赖外部指标（用户数、活跃度、影响力）
- 依赖内在感受（功能实现、用户体验、项目质量）
- 主观判断，而非客观数据

**衡量方式**：
- 你自己对项目功能实现的满意度
- 用户对项目体验的满意度
- 项目本身的质量和完整性

## 🚫 非目标

### 不替代现有工具

| 工具 | 非目标 | 理由 |
|------|--------|------|
| **Terraform** | 不管云资源全生命周期 | 范围太大，不是 AgentPlane 的定位 |
| **Kubernetes** | 不做容器编排 | 复杂度太高，不是 AgentPlane 的目标 |
| **Ansible** | 不做配置编排 | 偏 Agent 任务入口和证据，不偏配置执行 |
| **CI/CD 工具** | 不做持续集成/持续部署 | 专注于产品生命周期管理 |
| **监控工具** | 不做实时监控 | 专注于运维管理，不专注于实时监控 |

### 不服务的场景

| 场景 | 非目标 | 理由 |
|------|--------|------|
| **大型企业** | 不支持大型多租户平台 | 目标用户是小团队和个人开发者 |
| **强一致场景** | 不支持强一致持续调谐 | 不是常驻 reconciler |
| **实时系统** | 不支持实时系统 | 专注于产品生命周期管理 |

### 不成为的形态

| 形态 | 非目标 | 理由 |
|------|--------|------|
| **SaaS** | 不做托管服务 | 当前阶段不适合，需要专注核心功能 |
| **通用 Agent 框架** | 不做通用 Agent 框架 | 专注于产品生命周期管理 |
| **大型 DevOps 平台** | 不做大型 DevOps 平台 | 目标用户是小团队和个人开发者 |

### 不管的内容

| 内容 | 非目标 | 理由 |
|------|--------|------|
| **业务开发** | 不管代码编写、代码审查、单元测试 | 这些是人类的工作 |
| **代码编辑** | 不做代码编辑器 | 留给专业工具 |
| **版本控制** | 不做版本控制系统 | 留给 Git 等工具 |

### 与常见工具的边界

| 工具或模式 | 边界 |
| --- | --- |
| Shell scripts | 脚本可作为内部实现资产，但不能成为正式入口。 |
| Ansible | Ansible 偏配置执行编排；AgentPlane 偏 Agent 任务入口、证据、台账和文档回写。 |
| Terraform | Terraform 偏声明云资源；AgentPlane 偏已存在主机和应用交付闭环。 |
| 1Panel / Docker Compose | 这些是可被管理的 substrate；正式任务入口仍是 `agentplane ...`。 |
| 应用仓库 CI/CD | 应用仓库负责构建和测试自身；AgentPlane 负责正式部署、验证和控制面记录。 |

## 📋 项目定义

### 项目层级

```
项目（Project）
├── 业务系统（Business System）
│   ├── 应用（Application）
│   └── ...
├── 业务系统（Business System）
│   ├── 应用（Application）
│   └── ...
└── 全局配置（Global Config）
```

### 配置管理

- **声明方式**：应用通过配置文件（如 `config.yaml`）声明配置
- **管理方式**：Agent 负责配置的存储、同步、验证

### 操作粒度

| 操作类型 | 负责方 | 包含的操作 |
|----------|--------|------------|
| **业务开发** | 人类 | 需求分析、架构设计、代码实现、代码审查、单元测试 |
| **运维相关** | AgentPlane | 构建、部署、监控、运维、故障排查 |

## 📊 成熟度口径

当前项目是 alpha。可依赖的是仓库治理、文档治理、离线门禁、CLI-first 约束和 secrets 边界；仍在收敛的是发布自动化、provider 合同、app delivery schema 和 live gate 自动化。

## ⚠️ 约束条件

### 资源约束

| 资源 | 约束 |
|------|------|
| **维护者** | 单人维护（当前） |
| **时间** | 业余时间投入 |
| **资金** | 无商业收入 |

### 技术约束

| 约束 | 说明 |
|------|------|
| **Python 3.12+** | 唯一运行时 |
| **PyYAML>=6.0** | 唯一运行时依赖 |
| **uv** | 包管理器 |
| **Ruff** | 代码风格和格式化 |

### 设计约束

| 约束 | 说明 |
|------|------|
| **CLI-first** | 所有操作通过统一入口 |
| **Agent-first** | AI 友好设计 |
| **可 fork** | 用户可以 fork 后定制 |
| **离线优先** | 默认测试设计为确定性和离线 |

## 🔗 假设与依赖

### 假设

| 假设 | 风险 | 应对 |
|------|------|------|
| 小团队需要 AI 辅助运维 | 市场需求不足 | 通过真实用户验证 |
| CLI-first 是正确的技术选择 | 用户不习惯 CLI | 提供文档和教程 |
| 开源模式可持续 | 维护者 burnout | 建立社区，分散维护 |

### 依赖

| 依赖 | 说明 | 风险 |
|------|------|------|
| Python 生态 | 运行时和工具链 | 低风险 |
| GitHub | 代码托管、CI/CD | 低风险 |
| 1Panel | 当前主要 Provider | 中风险（Provider 合同待稳定） |
| WSL | Windows 开发环境 | 低风险 |

## 💡 决策理由

**为什么选择"给 Agent 的产品全生命周期控制面"这个定位？**

1. **聚焦核心价值**：专注于 Agent 和产品全生命周期，避免范围过大
2. **明确目标用户**：同时面向四种用户，但共同特点是资源有限、需要自动化
3. **内在成功标准**：用户满意度，而非外部指标，更符合项目本质
4. **清晰边界**：明确不做什么，避免资源分散

**为什么不是其他定位？**

| 替代方案 | 不选择的理由 |
|----------|-------------|
| 通用 Agent 框架 | 范围太大，无法聚焦，需要更多资源 |
| 大型 DevOps 平台 | 目标用户不匹配，复杂度太高 |
| SaaS 服务 | 需要更多资源，不符合"可 fork"理念 |
