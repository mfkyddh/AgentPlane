# 四层体系审查清单

结论：四层体系（战略层、项目层、工程层、技术层）各有明确的审查节奏和检查点。本文定义每层的审查频率、检查项和判定标准，确保文档与实践持续对齐。

---

## 审查节奏总览

| 层级 | 审查频率 | 审查时机 | 审查者 |
|------|----------|----------|--------|
| 战略层 | 季度审查 | 每季度末或重大战略调整时 | 维护者 |
| 项目层 | 月度审查 | 每月末或项目阶段转换时 | 维护者 |
| 工程层 | 每次 PR | Pull Request 提交时 | 维护者/贡献者 |
| 技术层 | 每次发布 | 版本发布前 | 维护者/贡献者 |

---

## 战略层审查清单（季度审查）

**审查目标**：确认战略方向正确、决策记录完整、原则被遵循

**关联文档**：[愿景](../strategy/vision.md)、[原则](../strategy/principles.md)、[路线图](../strategy/roadmap.md)、[决策记录](../strategy/decisions/)

### 检查项

| # | 检查项 | 判定标准 | 通过 |
|---|--------|----------|------|
| S1 | 愿景是否还正确？ | 愿景仍能回答"我们要去哪里"，与当前市场/技术环境不矛盾 | [ ] |
| S2 | 非目标是否需要调整？ | 非目标列表仍反映当前约束和边界，没有过时的排除项 | [ ] |
| S3 | 原则是否被遵循？ | 近期决策和实现与哲学原则、工程原则一致 | [ ] |
| S4 | 路线图是否需要调整？ | 三阶段路线图的阶段划分、里程碑和优先级仍然合理 | [ ] |
| S5 | 决策记录是否完整？ | 所有重大战略决策都有对应的 decision record | [ ] |
| S6 | 决策记录是否需要归档？ | 已完成或已推翻的决策标记为 superseded | [ ] |
| S7 | 蓝图是否需要更新？ | 终极蓝图与当前路线图保持一致 | [ ] |

### 判定规则

- 全部通过：战略层健康，无需调整
- 存在未通过项：标记问题，安排调整任务
- S1 或 S3 未通过：立即召开战略审查会议

---

## 项目层审查清单（月度审查）

**审查目标**：确认项目按计划推进、风险可控、角色职责清晰

**关联文档**：[项目章程](../project/charter.md)、[角色与职责](../project/roles.md)、[沟通机制](../project/communication.md)、[风险管理](../project/risk-management.md)

### 检查项

| # | 检查项 | 判定标准 | 通过 |
|---|--------|----------|------|
| P1 | 项目进度如何？ | 当前阶段进度与路线图一致，无重大偏差 | [ ] |
| P2 | 风险是否可控？ | 风险登记册中无新增高风险项，已有风险有应对措施 | [ ] |
| P3 | 角色职责是否清晰？ | 各角色职责无重叠或真空，新角色已文档化 | [ ] |
| P4 | 沟通机制是否有效？ | 决策流程、反馈渠道、状态报告机制正常运转 | [ ] |
| P5 | 章程是否需要更新？ | 项目目标、范围、约束与当前实际一致 | [ ] |
| P6 | 资源是否充足？ | 人力、工具、环境资源满足当前阶段需求 | [ ] |
| P7 | 依赖是否明确？ | 外部依赖（第三方服务、上游项目）状态清晰 | [ ] |

### 判定规则

- 全部通过：项目层健康，继续推进
- 存在未通过项：标记问题，纳入下月计划
- P1 或 P2 未通过：立即评估是否需要调整计划

---

## 工程层审查清单（每次 PR）

**审查目标**：确保代码质量、测试充分、文档同步、规范遵循

**关联文档**：[代码风格](code-style.md)、[Git 规范](git-conventions.md)、[测试架构](testing-architecture.md)、[测试规范](testing-conventions.md)、[发布流程](release-process.md)

### 检查项

| # | 检查项 | 判定标准 | 通过 |
|---|--------|----------|------|
| E1 | 代码风格是否符合？ | 通过 `ruff check .` 和 `ruff format .` | [ ] |
| E2 | 测试是否充分？ | 新增/修改代码有对应测试，测试标记正确（unit/integration/e2e） | [ ] |
| E3 | 文档是否更新？ | 影响用户/开发者的变更已更新相关文档 | [ ] |
| E4 | 提交规范是否遵循？ | Commit message 符合 Conventional Commits 格式 | [ ] |
| E5 | 链接是否完整？ | 新增/修改文档的链接指向正确目标 | [ ] |
| E6 | Secret 是否泄露？ | 无真实 secret 进入代码或文档 | [ ] |
| E7 | 健康检查是否通过？ | 通过 `agentplane repo health-check --repo-root .` | [ ] |
| E8 | 变更范围是否合理？ | 单个 PR 聚焦单一目的，不混入无关改动 | [ ] |

### 判定规则

- E1 或 E7 未通过：阻断合并，修复后重新提交
- E2 或 E6 未通过：阻断合并，补充测试或移除 secret
- E3 或 E4 未通过：建议修复，可由 reviewer 决定是否阻断
- E5 或 E8 未通过：建议修复，不阻断合并

## 技术层审查清单（每次发布）

**审查目标**：确保架构合理、性能达标、安全满足、运维就绪

**关联文档**：[核心架构合同](../architecture/control-plane.md)、[技术栈约束](tech-stack.md)、[跨平台规范](cross-platform.md)、[威胁模型](threat-model.md)

### 检查项

| # | 检查项 | 判定标准 | 通过 |
|---|--------|----------|------|
| T1 | 架构是否合理？ | 变更符合架构合同，未引入违反边界的新依赖 | [ ] |
| T2 | 性能是否达标？ | 无明显性能退化，关键路径响应时间在可接受范围 | [ ] |
| T3 | 安全是否满足？ | 通过威胁模型审查，无新增高风险漏洞 | [ ] |
| T4 | 运维文档是否完整？ | 发布相关的 runbook 已更新，回滚方案已文档化 | [ ] |
| T5 | 跨平台是否兼容？ | Windows/WSL/Linux 行为一致，路径策略正确 | [ ] |
| T6 | 向后兼容是否保持？ | 破坏性变更有迁移指南或版本标记 | [ ] |
| T7 | 依赖是否安全？ | 新增依赖经过评估，无已知高危漏洞 | [ ] |
| T8 | 监控是否就绪？ | 关键指标有监控，告警规则已配置 | [ ] |

### 判定规则

- T1 或 T3 未通过：阻断发布，修复后重新评估
- T2 或 T5 未通过：评估影响范围，决定是否阻断
- T4 或 T6 未通过：补充文档或迁移指南后发布
- T7 或 T8 未通过：记录风险，决定是否接受或延迟发布

## 审查结果记录

### 记录模板

```markdown
## 审查记录：[层级] [日期]

**审查者**：[姓名]
**审查范围**：[具体范围]

### 通过项
- [列出通过的检查项]

### 未通过项
- [检查项编号]：[问题描述] → [处理决定]

### 后续行动
- [行动项1]：[负责人] [截止日期]
- [行动项2]：[负责人] [截止日期]
```

### 记录存放

- 战略层审查记录：`docs/strategy/decisions/` 或项目管理工具
- 项目层审查记录：项目管理工具或会议纪要
- 工程层审查记录：PR review comments
- 技术层审查记录：发布 notes 或 `docs/history/`
