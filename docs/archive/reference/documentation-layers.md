# 🏗️ 四层文档体系

结论：AgentPlane 采用四层文档体系（战略层、项目层、工程层、技术层），确保文档分层清晰、职责明确、相互支撑。

---

## 📖 四层体系概述

```
┌─────────────────────────────────────────────────────────────┐
│                    战略层 (Strategy)                         │
│         愿景 → 原则 → 路线图 → 决策记录                      │
│         回答：去哪里？为什么？                                │
├─────────────────────────────────────────────────────────────┤
│                    项目层 (Project)                          │
│         目标 → 范围 → 进度 → 资源 → 风险                     │
│         回答：做什么？谁来做？何时做？                        │
├─────────────────────────────────────────────────────────────┤
│                    工程层 (Engineering)                      │
│         流程 → 标准 → 工具 → 质量 → 协作                     │
│         回答：如何做？如何保证质量？                          │
├─────────────────────────────────────────────────────────────┤
│                    技术层 (Technical)                        │
│         架构 → 规范 → 实现 → 运维 → 验证                     │
│         回答：具体怎么做？如何维护？                          │
└─────────────────────────────────────────────────────────────┘
```

---

## 📖 各层定义

### 战略层 (Strategy)

**定义**：决定项目的方向、价值和边界

**核心问题**：
- 我们要去哪里？（愿景）
- 为什么？（原则）
- 如何到达？（路线图）
- 为什么这样做？（决策记录）

**文档位置**：`docs/strategy/`

**主要文档**：
- 愿景 (`vision.md`)
- 原则 (`principles.md`)
- 路线图 (`roadmap.md`)
- 决策记录 (`decisions/`)

**更新频率**：低频（季度/年度）

**决策者**：维护者

---

### 项目层 (Project)

**定义**：将战略转化为可执行的计划，管理进度、资源和风险

**核心问题**：
- 做什么？（目标和范围）
- 谁来做？（角色和职责）
- 何时做？（进度和里程碑）
- 需要什么？（资源和约束）
- 可能出什么问题？（风险和应对）

**文档位置**：`docs/project/`

**主要文档**：
- 主线追踪器 (`backlog.md`)
- 愿景中的约束和干系人 (`../strategy/vision.md`)

**更新频率**：中频（月度/季度）

**决策者**：维护者

---

### 工程层 (Engineering)

**定义**：定义如何高质量地交付软件

**核心问题**：
- 如何开发？（开发流程）
- 如何保证质量？（质量标准）
- 用什么工具？（工具链）
- 如何协作？（协作规范）

**文档位置**：`docs/reference/`

**主要文档**：
- 代码风格 (`code-style.md`)
- Git 规范 (`git-conventions.md`)
- 测试架构 (`testing-architecture.md`)
- 测试规范 (`testing-conventions.md`)
- 发布流程 (`release-process.md`)
- 仓库结构 (`repository-structure.md`)
- 文档治理 (`documentation-governance.md`)

**更新频率**：中频（月度/季度）

**决策者**：维护者

---

### 技术层 (Technical)

**定义**：具体的架构设计、技术规范和实现细节

**核心问题**：
- 如何设计？（架构）
- 如何实现？（规范）
- 如何维护？（运维）
- 如何验证？（测试）

**文档位置**：
- 架构：`docs/architecture/`
- 规范：`docs/reference/`
- 运维：`docs/runbooks/`
- 开发：`docs/developer/`（待建）

**主要文档**：
- 核心架构合同 (`architecture/control-plane.md`)
- 协作边界 (`architecture/agentplane-app-collaboration.md`)
- 技术栈约束 (`reference/tech-stack.md`)
- 跨平台规范 (`reference/cross-platform.md`)
- 威胁模型 (`reference/threat-model.md`)
- 运维手册 (`runbooks/`)

**更新频率**：高频（按需）

**决策者**：维护者/贡献者

## 🔗 层级关系

### 向下指导

```
战略层 → 项目层 → 工程层 → 技术层
```

- **战略层指导项目层**：愿景和路线图指导项目目标和里程碑
- **项目层指导工程层**：项目计划分解为具体的工程任务
- **工程层指导技术层**：工程标准约束技术实现

### 向上反馈

```
技术层 → 工程层 → 项目层 → 战略层
```

- **技术层反馈工程层**：技术实践验证工程流程
- **工程层反馈项目层**：工程执行结果反馈项目计划
- **项目层反馈战略层**：项目进展验证战略假设

### 平行协同

- **战略层与技术层**：战略决策需要技术可行性评估
- **项目层与工程层**：项目计划需要工程能力支撑

## 📌 文档治理

### 文档标准

所有文档必须遵循 [文档治理规范](documentation-governance.md)：

- **Frontmatter**：必须包含 status、owner、last_verified、audience
- **结论先行**：文档开头必须有结论
- **链接完整**：必须有"关联文档"部分
- **定期验证**：必须定期更新 last_verified

### 文档更新

| 层级 | 更新频率 | 更新触发 |
|------|----------|----------|
| **战略层** | 低频 | 战略调整、重大决策 |
| **项目层** | 中频 | 项目阶段、重大变更 |
| **工程层** | 中频 | 流程改进、工具变更 |
| **技术层** | 高频 | 功能开发、问题修复 |

### 文档审查

- **战略层文档**：维护者审查
- **项目层文档**：维护者审查
- **工程层文档**：维护者审查
- **技术层文档**：维护者或贡献者审查

## 🛠️ 实施指南

### 新增文档

1. **确定层级**：根据文档内容确定属于哪一层
2. **遵循标准**：遵循文档治理规范
3. **建立链接**：在相关文档中添加链接
4. **更新索引**：更新对应层的索引文档

### 文档重构

1. **评估层级**：评估文档是否在正确的层级
2. **检查重复**：检查是否有重复内容
3. **建立链接**：建立正确的链接关系
4. **更新引用**：更新所有引用

### 文档归档

1. **评估状态**：评估文档是否仍然活跃
2. **更新状态**：更新 frontmatter status
3. **移动位置**：移动到 archive 目录
4. **更新链接**：更新所有链接

## ✅ 审查节奏

| 层级 | 审查频率 | 审查时机 | 审查者 |
|------|----------|----------|--------|
| 战略层 | 季度审查 | 每季度末或重大战略调整时 | 维护者 |
| 项目层 | 月度审查 | 每月末或项目阶段转换时 | 维护者 |
| 工程层 | 每次 PR | Pull Request 提交时 | 维护者/贡献者 |
| 技术层 | 每次发布 | 版本发布前 | 维护者/贡献者 |

### 战略层检查项（季度）

| # | 检查项 | 判定标准 |
|---|--------|----------|
| S1 | 愿景是否还正确？ | 愿景仍能回答"我们要去哪里" |
| S2 | 非目标是否需要调整？ | 非目标列表仍反映当前约束和边界 |
| S3 | 原则是否被遵循？ | 近期决策和实现与原则一致 |
| S4 | 路线图是否需要调整？ | 阶段划分、里程碑和优先级仍然合理 |
| S5 | 决策记录是否完整？ | 所有重大战略决策都有对应的 decision record |

### 工程层检查项（每次 PR）

| # | 检查项 | 判定标准 |
|---|--------|----------|
| E1 | 代码风格 | 通过 `ruff check .` 和 `ruff format .` |
| E2 | 测试充分 | 新增/修改代码有对应测试 |
| E3 | 文档更新 | 影响用户的变更已更新文档 |
| E4 | 提交规范 | Commit message 符合 Conventional Commits |
| E5 | Secret 安全 | 无真实 secret 进入代码或文档 |
| E6 | 健康检查 | 通过 `agentplane repo health-check` |

### 技术层检查项（每次发布）

| # | 检查项 | 判定标准 |
|---|--------|----------|
| T1 | 架构合理 | 变更符合架构合同 |
| T2 | 安全满足 | 通过威胁模型审查 |
| T3 | 运维文档 | 发布相关 runbook 已更新 |
| T4 | 跨平台兼容 | Windows/WSL/Linux 行为一致 |
