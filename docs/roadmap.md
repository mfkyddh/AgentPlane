# 路线图

> 结论：从 Alpha 到"小团队标准工具"分三个阶段推进。每个阶段有明确的完成标准，通过实践验证而非计划驱动。

---

## 当前状态：Alpha

> Alpha 的目标是夯实核心，确保基础可靠。

### 已稳定可依赖

- 仓库治理（`repo health-check`、`release-check`）
- CLI 入口纪律（正式操作通过 `agentplane ...`）
- 离线测试门禁、文档治理、Secret 边界

### 仍在收敛

- 公开安装体验（发布产物未自动化）
- Provider 合同（合同测试待扩展）
- App delivery schema（schema_version: 2 仍在扩展）
- Live gate（需要准备环境）

### 完成标准

- [ ] 所有核心 Skill 有完整测试
- [ ] 文档体系覆盖所有目标用户场景
- [ ] 至少一个真实应用（App）完成全生命周期验证

---

## 三阶段路线

```
Alpha（当前）          Beta                   GA
─────────────────────────────────────────────────────→
  夯实核心             开放验证               规模扩展

  • CLI 骨架稳定       • 外部用户可用         • 100+ 用户
  • 文档体系完整       • Provider 合同稳定    • 社区自运转
  • 离线测试覆盖       • App delivery 成熟    • 插件生态
```

**为什么是三个阶段？**

- **Alpha → Beta**：内部验证完成后，才能让外部用户使用。核心不稳就开放，会浪费用户信任。
- **Beta → GA**：外部用户验证完成后，才能规模扩展。没有真实用户反馈就推广，会放大问题。
- 每个阶段的退出标准都是可验证的，不靠"感觉差不多了"。

---

## Beta 阶段

> Beta 的目标是开放验证，让外部用户可用。

### 关键里程碑

| 里程碑 | 目的 | 验收标准 |
|--------|------|----------|
| M1: 公开贡献者循环 | 外部 PR 可自验证 | 贡献者文档完整，CI 可公开访问 |
| M2: 发布工程 | tag 可复现 | 自动化发布流程，版本号规范 |
| M3: 合同硬化 | 交付合同可机器检查 | contract.yaml schema 稳定，验证工具可用 |
| M4: 运行时拆分 | 降低风险 | 核心逻辑与 provider 解耦 |
| M5: Provider 合同 | provider 细节隔离 | provider 接口稳定，可替换 |

### 里程碑逻辑

M1 → M2 → M3 是**基础设施**：没有公开贡献者循环，外部用户无法参与；没有发布工程，版本不可复现；没有合同硬化，交付不可靠。M4 → M5 是**架构优化**：在基础设施稳定后，再做运行时拆分和 provider 隔离。

### 退出标准

- [ ] 至少 10 个外部用户成功使用
- [ ] Provider 合同稳定
- [ ] App delivery schema 正式发布

---

## GA 阶段

> GA 的目标是规模扩展，成为小团队标准工具。

### 关键能力

- 插件生态：支持第三方扩展
- 社区建设：外部贡献者维护
- 标准定位：成为小团队 AI-assisted 运维的标准选择

### 退出标准

- [ ] 100+ 活跃用户
- [ ] 社区自运转（外部贡献者维护）
- [ ] 至少 3 个成功案例文档化
